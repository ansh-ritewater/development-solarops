# Product & Lifecycle Gaps Audit

**Investigated 21-22 August 2026 via fresh, direct code reads.** Pure
documentation — nothing fixed, nothing built. Ansh's decision: fix
none of this now; document completely first, revisit when ready to
start. Companion to the 5-pass platform audit
(FILTER_AUDIT.md/FEATURE_AUDIT.md/BACKEND_ROADMAP_AUDIT.md/
PERFORMANCE_AUDIT.md/SECURITY_AUDIT.md).

## Origin

Ansh received external AI-generated suggestions for improving lead
tracking. Rather than implement any of them on faith, each was
independently verified against the real codebase — one suggestion's
own premise turned out to be wrong about how this app actually works,
and needed correcting before it could be evaluated at all.

## Gap 1 — No lead ever gets a clock, confirmed manual assignment,
confirmed zero escalation of any kind

**Confirmed:** task assignment at creation (New Task and Bulk Upload,
both paths) is 100% a manual admin choice, every time — never
automatic, and a lead can be left genuinely unassigned indefinitely.
Zero "opened/viewed by engineer" concept exists anywhere in the data
model. Zero escalation/alerting mechanism exists in any form.

**Ansh's decision, 22 Aug 2026: manual assignment itself stays exactly
as-is — nothing to change there.** The gap being tracked is purely the
missing clock/escalation on top of that manual process, not the
manual process itself.

**The real fix, precisely two-phased:**
- **Phase A — no backend needed, buildable standalone:** a visual
  "assigned N hours ago, still untouched" indicator, using only
  `createdAt`/`assignedTo` (both already exist). Can only approximate
  "unopened" via "time since assignment," not true viewing — the data
  to know the difference doesn't exist yet.
- **Phase B — genuinely backend-dependent:** requires a new `viewedAt`
  field (small, client-side, contained — write it once, on first
  real open) PLUS a scheduled server-side check (Cloud Scheduler + a
  Cloud Function) to notice "24 hours, still unviewed" and fire a real
  notification. This is the same infrastructure already tracked as
  item #5 in `PARKED.md`'s consolidated backend list (push
  notifications) — not a new, separate backend need.

**Ansh's decision: fix properly and completely, not now.** Both
phases documented; whether to do Phase A alone first, or wait and do
both together once notification infrastructure exists, is an open
sequencing decision for whenever this is picked up.

## Gap 2 — Drop reason is not reliably captured, worse than the
original suggestion assumed

**Confirmed:** exactly two ways a task ever becomes Dropped — Field
Review's "Reject" decision, and Admin Override. Only the Field Review
path writes a real `droppedReason`; Admin Override never populates it
at all, only a generic stage-history note. **Confirmed by Ansh: Admin
Override is the daily, primary mechanism used for drops** — meaning
the majority of real drops today have no structured reason captured,
not a rare edge case.

**The original external suggestion ("replace typed reason with a
fixed list") targeted the wrong problem** — the issue isn't
free-text-vs-dropdown, it's that the primary drop path asks for no
reason at all today.

**Ansh's decision: fix properly and completely, not now.** Real fix
needs: a required reason field added to the Admin Override flow when
dropping (list-plus-detail-box, per the original suggestion's actual
good idea, just applied to the correct flow), and a decision on
whether Field Review's existing free-text path should also move to
the same list-plus-detail pattern for consistency.

## Gap 3 — Most "free text" is already solved; only 2 fields are
real candidates

**Confirmed:** State, District, Lead Source, and Engineer assignment
are already dropdowns — not free text. The Survey template's own
custom-field system already fully supports a genuine dropdown type
today — any admin building a custom question can already choose
"select" over "text," no code change needed.

**The only 5 genuinely free-text fixed fields, confirmed exhaustively:**
Title, Description, Employee Name, Lead Generated By Note, Blocked
Reason. Of these, **Title/Description/Blocked Reason are NOT real
candidates** — each is inherently unique or situational per task;
converting them to a dropdown would harm usability, not help it.

**Only Employee Name and Lead Generated By Note are genuine
candidates** — small, contained changes. The one real dependency: no
"employee roster" master list exists yet (unlike districts/lead
sources, which already have one) — needs building first, mirroring
the existing `leadSources` admin-managed-list pattern.

**Ansh's decision: fix properly and completely, not now.**

## Gap 4 — No timestamp for when a sale was actually closed

**Confirmed:** `saleClosed` is purely a boolean; `saleClosedSource` is
only `'auto'|'manual'`; no dedicated date field exists anywhere. The
only timestamp that moves is the task's generic `updatedAt`, which
gets overwritten by any later, unrelated edit — meaning there is
currently no reliable way to answer "when was this sale actually
closed," even approximately.

**Two honestly-sized options, confirmed:**
- **Minimal, available today, zero code change:** an admin can add
  their own custom `'date'`-type Survey/Documents field right now —
  purely additive, but not wired into the actual detection logic.
- **The real version:** a genuine `saleClosedAt`, auto-stamped the
  moment detection first flips true — a contained but multi-site
  change (5 real write sites: `useTaskSubmit.ts`,
  `DocumentsWorkDrawer.tsx`, `TaskQueueProcessor.tsx`,
  `usePipelineActions.ts`, `useTaskActions.ts`'s manual functions),
  plus one real design decision: does the timestamp persist or
  reset when `resetSaleClosedToAuto` is used?

**Ansh's decision: fix properly and completely, not now.**

## Gap 5 — No lead-lifecycle duration tracking exists, anywhere,
past the current stage

**Confirmed:** no dedicated per-stage entry/exit timestamps exist. The
only structured data is `stageHistory`, and every "days in stage"
calculation anywhere in the app (found duplicated 3 separate times,
independently written) only ever answers "time in the CURRENT stage"
— never "how long did this task spend in a stage it already left."
The raw data to compute real historical per-stage durations already
exists in every task (pairing consecutive `stageHistory` timestamps),
but nothing anywhere performs that pairing today.

**Real caveat:** `stageHistory` is capped at 50 entries per task — a
heavily-corrected task's oldest transitions are silently dropped,
meaning any future historical-duration feature would be incomplete
for such tasks specifically.

**This directly matches Ansh's own broader observation**: real
lifecycle tracking effectively stops working after Survey — nothing
currently answers "how long is a lead taking at each stage, from
start to conversion."

## Gap 6 — Excel export and Reports both have real, confirmed
completeness gaps

**Excel export (`exportTasksToExcel.ts`):** confirmed absent
entirely — correction status, remarks (proposal/backend), and any
per-stage duration data. `droppedReason` column exists but will be
blank for the majority of real drops per Gap 2's finding.

**A real, separate small bug found along the way:** the Excel
export's "Conversion Date" and the Reports page's own separate CSV
export's "Conversion Date" are computed two different ways for the
same conceptual field — the Excel version from the generic,
overwritable `updatedAt`; the Reports version correctly from the
actual `stageHistory` entry. Same "two implementations quietly
disagreeing" pattern already found and fixed 4 separate times
elsewhere in this project.

**Reports page:** confirmed not empty — 8 distinct charts/tables plus
3 separate export mechanisms (main Excel export + 2 independent CSVs
from Reports itself) — but none include correction status, remarks,
or duration data either. Whether it's genuinely useful for real daily
work is Ansh's own judgment call, not something code alone can
answer — full current inventory now on record for whenever a
redesign is considered.

**RESOLVED 22 Aug 2026** — the Excel export gap is now fixed:
correction status, Proposal/Backend remarks, per-stage Application
Journey completion dates AND photos are all now included, plus the
Conversion Date disagreement with Reports' own export is corrected
to use the same real `stageHistory`-derived value. Confirmed
already visible, read-only, to field engineers: Lead Source needed
no change at all.
Two real implementation bugs found and fixed during testing, both
live-tested by Ansh before being accepted:
1. Journey-step columns initially ordered by whichever task
   happened to sort first in the export batch, rather than the
   real, correct process sequence — fixed by using one genuine
   reference task's own permanently-fixed step order (Loan
   preferred, since its 18 steps are the superset containing
   Cash's 16 in their correct positions) instead.
2. When photo columns were added for the "Images of Installed
   Solar Panels" step, the completion-date column for that same
   step was accidentally REPLACED instead of kept — every step,
   photo or not, now correctly gets its own date column first, with
   photo-type steps adding photo-slot columns after it, never
   instead of it.
Photo columns are built generically for any photo-type Application
Journey step (not hardcoded to this one label), so this continues
working correctly if an admin ever renames it or adds another
photo-type step later. Reports page's own separate CSV exports
remain untouched and still have the same gaps — Ansh has confirmed
Reports isn't in active use, so this was deliberately not extended
there.
One more real bug caught and fixed after the initial rebuild: the
export's row ordering used a plain alphabetical sort on Task #,
which put `T-1000` before `T-091` once counts passed 3 digits —
fixed to compare the numeric value instead. Both the Excel rebuild
and this sort fix are now confirmed deployed to production
(`solarops-ritesolar`), via real `firebase deploy` output and a live
re-export confirming correct sequencing on the actual production
site.
